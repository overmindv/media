# media

`media` — владелец файлов и изображений Overmindv. PostgreSQL хранит только метаданные и жизненный цикл, бинарные данные находятся в S3-совместимом object storage.

## Поток загрузки

1. Frontend вызывает GraphQL `createMediaUpload` в `api-gateway`.
2. Gateway передаёт доверенный actor context во внутренний HTTP API Media.
3. Media создаёт `pending_upload` и возвращает presigned POST либо multipart upload.
4. Браузер загружает байты напрямую в MinIO/S3 и вызывает `completeMediaUpload`.
5. Worker проверяет контрольную сумму, отправляет копию в ClamAV, проверяет ее MIME, создает WebP-варианты и переводит файл в `ready`.

При сбое ClamAV файл остается в карантине и проверяется повторно с задержкой до 256 секунд. Найденная сигнатура приводит к отказу. Для разработки можно явно задать `ENV=local` и `MEDIA_ALLOW_UNSCANNED_LOCAL=true`. В любых других окружениях приложение отклоняет такой флаг при запуске.

Файлы, опубликованные до появления признака `scan_verified`, не получают ссылки в обычном режиме. Для публикации загрузите их заново. Для обновления пилота сначала остановите старый Media, примените миграцию и запустите новую версию. Не возвращайте старый бинарник поверх новой схемы.

Очередь проверок доступна в Prometheus-формате на внутреннем `GET /metrics/scan`. Метрика `media_scan_backlog_jobs` включает ожидающие и обрабатываемые задания. При ошибке БД endpoint возвращает 503.

Фоновый воркер получает задачу на 2 минуты и продлевает lease каждые 30 секунд. Если воркер остановился, другой может забрать задачу после истечения lease. Результат принимает только текущий lease. Перед физическим удалением blob исключается из дедупликации, а активные привязки и сроки хранения проверяются в PostgreSQL.

Перед миграцией `202611200002_media_job_leases.sql` остановите все старые Media worker. Миграция освобождает зависшие задачи старой версии. Смешанный запуск старого и нового воркеров не поддерживается.

Повтор multipart complete не создает второй scan job. Если S3 уже собрал
объект, Media проверяет его метаданные и завершает сессию в PostgreSQL.

`MEDIA_ENABLE_UPLOAD_CLEANUP` выключен по умолчанию. Для пробного запуска на
тестовых данных включите его после миграции `202611200003_media_upload_cleanup.sql`
и выдачи Media прав `AbortMultipartUpload` и `ListMultipartUploadParts` только
для карантина. Worker разбирает до 20 записей каждого вида за проход:
истекшие сессии, незакрепленные ключи попыток и blob без ссылок на файлы.
Для blob действует настроенный срок удаления. Карантин очищается после
истечения сессии, с запасом на старые подписанные ссылки. Опубликованные
объекты и активные задания не затрагиваются. S3-объекты без записей в БД
проверяются отдельной сверкой.

В публичных ответах доступны только WebP из `variants/public/`. Маленькие изображения перекодируются без увеличения. Оригинал изображения может скачать только владелец. Оригиналы выдаются как вложения по подписанной ссылке с `no-store` и сроком не дольше 15 минут. Старые изображения без WebP в новом префиксе нужно загрузить заново для показа превью.

`media-renderer` запускается рядом с Media из отдельного образа без сети и учетных данных. Media передает проверенный файл и список размеров через Unix-сокет. При повторной загрузке уже готовые варианты переиспользуются.

Лимит исходника: 20 МиБ, 8192 пикселя на сторону и 160 МиБ для декодированных данных из расчета 8 байт на пиксель. На обработку всех размеров отводится 25 секунд. Compose из `infra` запускает renderer с 1 CPU, 384 МиБ RAM, 32 PID и временным диском 96 МиБ. Если renderer недоступен, Media не публикует файл и ставит задачу на повтор.

Байты не проходят через frontend API, gateway или PostgreSQL. Redis и ClickHouse сервису в базовой версии не нужны.

## Поддерживаемые файлы

- JPEG, PNG, WebP — до 20 MiB и 40 мегапикселей;
- avatar — только public JPEG/PNG/WebP до 5 MiB и 12 мегапикселей;
- PDF и OOXML — до 50 MiB;
- ZIP, TAR, GZIP — до 250 MiB;
- SVG, исполняемые файлы и видео отклоняются.

Обычные изображения получают WebP-варианты шириной 320, 768 и 1440 пикселей, аватары — 128, 320 и 768 пикселей. EXIF и другая metadata удаляются `libvips`.

Gateway разрешает публичные аватары batch-запросом до 100 `file_id`. Отдельный token Users даёт доступ только к идемпотентной замене binding `users/user_avatar/{user_id}`. Непривязанные готовые avatar-файлы старше 24 часов автоматически переводятся в soft delete.

### Привязки материалов и логотипов

Укажи отдельные `MEDIA_CONTENT_TOKEN` и `MEDIA_ENTITIES_TOKEN` длиной 32-256
печатных символов без пробелов. Без токена маршруты сервиса недоступны.
Каждый токен передается в `X-Media-Service-Token`; токен gateway не подходит.

| Сервис | Проверка файлов | Запись привязок |
| --- | --- | --- |
| Content | `POST /v1/internal/content/binding-files/check` | `PUT /v1/internal/content/materials/{material_id}/revisions/{revision_id}/bindings` |
| Entities | `POST /v1/internal/entities/binding-files/check` | `PUT /v1/internal/entities/logos/{entity_id}/bindings` |

Тело запроса содержит `actor_user_id` и массив `file_ids`. Content передает
до 32 файлов с назначением `content_image`, `attachment` или `archive`.
Entities передает один публичный файл с назначением `catalog_logo`. Media
проверяет владельца, статус `ready` и наличие чистого blob.

При наследовании Content передает `inherit_from_revision_id`. Для предварительной
проверки дополнительно передается `material_id`. Чужой файл допустим только при
действующей привязке в указанной ревизии того же материала. Content проверяет
доступ пользователя к исходной ревизии до вызова Media.

При записи сервис также передает положительный `version`. Полный список файлов
заменяет предыдущий, пустой массив `[]` снимает привязки. Повтор с тем же
набором и версией возвращает `204`; старую версию Media игнорирует. Замена
содержимого той же версии дает `409 BINDING_VERSION_CONFLICT`. Предварительная
проверка не резервирует файлы, поэтому Media повторяет ее при записи.

Пока хотя бы одна привязка активна, удаление файла возвращает `409 FILE_IN_USE`.
Снятие привязки не удаляет файл и не меняет его видимость.

## Запуск и проверка

Сервис запускается через каркас `parker`: `GET /health`, `GET /ready` (готовность включает PostgreSQL и S3), `GET /metrics` и middleware предоставляет parker. Ранее отдельный `media-worker` влит в основной бинарник как фоновой `Runnable` — обработка файлов (checksum, ClamAV, WebP-варианты) выполняется в том же процессе.

Основной локальный запуск выполняется из `../infra` командой `make up`. Для изолированной разработки:

```bash
cp .env.example .env
make migrate-up
make run
```

Проверки:

```bash
make test
make lint
make build
```

Внутренний API описан в [docs/api.md](docs/api.md). Все endpoints требуют `X-Media-Service-Token`. Gateway и Users используют разные tokens; пользовательский контекст принимается только от gateway в `X-User-ID` и `X-User-Roles`.
